# `WebAuthnCeremony.deferred`

Works like [`WebAuthnCeremony.server`](/docs/api/webauthnceremony.server), but answers a sign-up as soon as the passkey is created. It sends `POST {url}/register` in the background and retries requests that fail in transit. The account address comes from the passkey's public key, so the app gets the same address either way.

A sign-in with a passkey the [`webAuthn`](/docs/api/webAuthn) adapter already knows works the same way. It answers once the passkey's signature checks out against the stored public key, and sends `POST {url}/login` in the background.

## Usage

```ts
import { WebAuthnCeremony } from 'accounts'

const ceremony = WebAuthnCeremony.deferred({ url: 'https://example.com/webauthn' })
```

## Trade-offs

- The server session exists only once the server has stored the passkey, so a server request the app sends right after sign-up may not be signed in yet. The [`webAuthn`](/docs/api/webAuthn) adapter makes sign-ins and sign-outs wait for it, for up to 10 seconds. A registration still running after that is cancelled, so it can't replace the session that follows.
- If the server refuses the sign-up while the page is open, the adapter removes the account and keeps its public key on the device. A later sign-in with the passkey restores the account if the server did store it.
- If the server refuses a deferred sign-in, the ceremony ends the session in place, and the adapter removes the account (an `accountsChanged` event), as for a refused sign-up.
- A refusal that arrives after the page closed goes unnoticed. Use this ceremony where the page outlives the request and every server request waits for it, such as an embedded iframe.

## Parameters

### credentials

- **Type:** `RequestCredentials`
- **Default:** `"same-origin"{:js}`

Credential mode for ceremony requests.

### url

- **Type:** `string`
- **Required**

Base URL of the WebAuthn handler (e.g. `"https://example.com/webauthn"{:js}`).
