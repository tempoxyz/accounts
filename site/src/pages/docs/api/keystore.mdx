# `Keystore`

Pluggable backends for access-key material, configured per key type via [`Provider.create({ accessKey: { keystores } })`](/docs/api/provider#accesskeykeystores). A keystore owns access-key material end to end: `createKey()` provisions a key, and `toAccount()` turns a persisted record back into a signing account.

Keystores are about the device's key capabilities — [`Storage`](/docs/api/storage) persists provider state, keystores hold key material. This enables hardware-backed access keys (e.g. Secure Enclave / Android Keystore), remote signers (HSM, key-management services), and other custom backends. Records backed by `privateKey` or `keyPair` material hydrate unchanged, without consulting the keystore.

The default is `Keystore.defaults` — `{ p256: Keystore.webCryptoP256() }`.

## Interface

Apps with custom needs (own native module, HSM, remote signer) implement the two-function interface:

```ts
type Keystore = {
  /**
   * Whether handles hold live objects (e.g. a CryptoKey) that persist only
   * through structured-clone storage — on other storage the handle is
   * stripped at persist time, making the key session-only. When false
   * (default), handles must survive JSON serialization, portable across
   * all storage adapters.
   */
  requiresStructuredClone?: boolean
  /**
   * Creates access-key material. `handle` is opaque and persisted verbatim
   * by the SDK. Must fail loudly when runtime prerequisites are missing
   * (e.g. no Secure Enclave, no `crypto.subtle`) so provisioning errors
   * surface at authorization time, not at first sign.
   */
  createKey(): Promise<{ publicKey: Hex; handle: unknown }>
  /**
   * Turns a persisted key record back into a signing account.
   * Called once per launch; the SDK caches the result per record.
   */
  toAccount(
    record: { keyType: string; publicKey: Hex; handle: unknown },
    context: { access: Address; keyAuthorizationManager: KeyAuthorizationManager },
  ): Promise<Account> | Account
}
```

### Handles

The handle is opaque to the SDK: it is persisted verbatim alongside the access-key record (so material and record share one lifecycle — one write, one backup, one removal) and handed back to `toAccount` on hydration. Its schema is owned by whichever keystore wrote it; a `kind` discriminant is the conventional way to mark ownership.

### Errors

`toAccount` errors drive the record lifecycle:

- Throw `Keystore.KeyUnavailableError` when the key behind the handle is **permanently gone** (e.g. hardware key deleted, app keychain wiped). The SDK evicts the record so callers fall back to authorizing a fresh key.
- Throw any other error for handles the keystore does not recognize or **transient** failures (e.g. device locked): the record is kept and retried on next use.

### Composition

A keystore can compose multiple backends behind one slot (e.g. a hardware keystore with a software fallback for devices without a Secure Enclave). Gate provisioning fallback on a deliberate capability check — not on errors, so a transient failure never silently downgrades a hardware-capable device to a software key — and route hydration by the handle's own discriminant. When composing, treat `KeyUnavailableError` as an ownership claim: do not route the handle to another backend.

```ts twoslash
import { Keystore, Provider } from 'accounts'

declare function secureEnclave(options: { fallback: Keystore.Keystore }): Keystore.Keystore

const provider = Provider.create({
  accessKey: {
    keystores: {
      p256: secureEnclave({ fallback: Keystore.webCryptoP256({ extractable: true }) }),
    },
  },
})
```
