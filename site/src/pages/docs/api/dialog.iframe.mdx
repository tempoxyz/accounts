# `Dialog.iframe`

Creates an iframe dialog that embeds the auth app in a `<dialog>` element. This is the default on most browsers in secure (HTTPS) contexts.

Each provider attachment creates its own iframe session. Keep providers stable for the lifetime of the app so the iframe is not recreated between requests.

Visual appearance is configured via [`Dialog.Theme`](/docs/api/dialogs#dialogtheme), passed through the [`dialog`](/docs/api/dialog) adapter.

## Usage

```ts
import { dialog, Dialog, Provider } from 'accounts'

const provider = Provider.create({
  adapter: dialog({ dialog: Dialog.iframe() }),
})
```

## Fallback behavior

The iframe instance falls back to a popup in the following cases while handling a request:

- **Safari** — when a request uses `wallet_connect` or `eth_requestAccounts`. Safari does not support WebAuthn credential creation inside cross-origin iframes, so these methods are forwarded to a popup.
- **Untrusted host without IntersectionObserver v2** — when the host page is not in the wallet's trusted hosts list and the browser does not support IntersectionObserver v2 (used to detect iframe occlusion / clickjacking). A warning is logged and the request is forwarded to a popup. To opt the iframe back in, add your hostname to the trusted hosts list.
- **Mode switch from the auth app** — if the embedded auth app sends a `switch-mode` message, the iframe is hidden and any pending requests are forwarded to the popup for the remainder of the session.

In SSR environments (no `window`), `Dialog.iframe()` returns `Dialog.noop()`.
