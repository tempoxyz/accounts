# Playgrounds

Apps that sign in through Tempo ID, one per flow. Each uses `accounts` from the workspace, and the client ID that [`scripts/seed.ts`](https://github.com/tempoxyz/id/blob/main/scripts/seed.ts) in `tempoxyz/id` registers for it. Tempo ID's end-to-end tests drive these same apps.

| Playground                    | OAuth role                      | Flow                                                                                                          | Client ID                  | Port |
| ----------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------- | ---- |
| [`web`](web)                  | Public client                   | Headless sign-in with its own UI, single sign-on on reload, tokens in memory, calls `api`                     | `tempo-example-web`        | 5174 |
| [`web`](web), as `web-cash`   | Public client in its own realm  | The same, with accounts in the `tempo-cash` realm only: its own Privy app, and no passkey sign-in             | `tempo-example-web-cash`   | 5177 |
| [`web`](web), as `web-shared` | Public client in two realms     | The same, with accounts in the default and `tempo-cash` realms. A user with one in each chooses on sign-in    | `tempo-example-web-shared` | 5178 |
| [`wagmi`](wagmi)              | Public client in its own realm  | The flows of `web`, with the instance as its wagmi connector: each sign-in connects wagmi, and wagmi reads the account, the balance, and the sends | `tempo-example-wagmi`      | 5182 |
| [`mobile`](mobile)            | Public native client            | Signs in on Tempo ID's pages in the system browser, with a key, calls `api`                                    | `tempo-example-mobile`     | 8081 |
| [`third-party`](third-party)  | Third-party public client       | Registers nothing: serves its metadata document, signs in through Tempo ID's pages with an explicit key    | its document's URL         | 5180 |
| [`backend`](backend)          | Confidential client (BFF)       | Redirects to `/authorize`, keeps each session on its server with `BackendSession`, calls `api` from the server | `tempo-example-backend`    | 5175 |
| [`api`](api)                  | Resource server                 | Verifies Bearer tokens with `jose` against `/oauth2/jwks`, serves `/me`, and serves MPP payments under `/mpp` | none                       | 5176 |
| [`cli`](cli)                  | Public device client            | Signs in through the device grant with an access key, then funds, sends, and pays MPP endpoints with it          | `tempo-cli`                | none |

## Local runs

`pnpm dev` from the root of `tempoxyz/id` starts Tempo ID, the [local chain](https://github.com/tempoxyz/id/blob/main/docs/development/local.md#local-chain), `api`, `backend`, `third-party`, `wagmi`, `web`, `web-cash`, and `web-shared` in Docker on OrbStack, as the [development docs](https://github.com/tempoxyz/id/blob/main/docs/development/local.md) describe. Each runs as the service `playground-<name>`, at `https://playground-<name>--<hash>.tempo.local`. Start `mobile` on the host:

```sh
pnpm dev                                    # Tempo ID and every playground but mobile
EXPO_PUBLIC_API_URL=https://playground-api--<hash>.tempo.local \
EXPO_PUBLIC_TEMPO_ID_URL=https://id--<hash>.tempo.local \
EXPO_PUBLIC_TEMPO_RPC_URL=https://rpc--<hash>.tempo.local \
  pnpm --filter playground-mobile ios       # the iOS Simulator, which needs Xcode
```

`pnpm dev` prints the stack's Tempo ID URL, whose `<hash>` the other services share. Without these variables, `mobile` calls `http://localhost:5173` and `http://127.0.0.1:5176`, where no stack listens.

- **HTTPS:** Tempo ID registers only `https` redirect URIs for web apps, so the browser playgrounds run in the stack, where OrbStack serves HTTPS. The seed registers each app at its stack's domain.
- **Realms:** the seed sets the realms of `web-cash` and `web-shared` in the database. With the values that `pnpm env:pull` writes to `.env`, the `default` realm uses the test Privy app. Otherwise, and in `tempo-cash`, the stack creates a realm's accounts with secp256k1 keys that Tempo ID holds, as the [realm settings](https://github.com/tempoxyz/id/blob/main/docs/realms.md#settings) describe.
- **Third-party app:** `third-party` serves its [metadata document](https://github.com/tempoxyz/id/blob/main/docs/apps.md#metadata-document) at `/.well-known/oauth-client-metadata.json`, for the origin in `PUBLIC_URL`, or the request's host without it. Its client ID is that URL, so the seed registers nothing for it. It signs in through the embedded dialog or a redirect, with the same permissions form, key, sections, and transfers as `web`. Its form starts at 10 OUSD for a day, in `transfer`, `transferWithMemo`, and the channel reserve's `open` and `topUp`, and a cleared expiry, limit list, or scope list shows the `missing_permissions` refusal. `PERMISSIONS` replaces the form. It holds its sign-in only in the page, so a reload signs the user out of the app, and its sign-out forgets the key without ending the Tempo ID session.
- **Sign-in modes:** `web`, `wagmi`, and `third-party` offer **Sign in via dialog**, then **Sign in via redirect**. The dialog falls back to a popup as [`Actions.dialog.signIn`](../docs/api/Actions.dialog.signIn.md) describes. `web` signs the dialog in through a popup with `?dialog=popup`, as the end-to-end suite does.
- **Backend secret:** the seed stores `BACKEND_CLIENT_SECRET` from `.env` as the secret of `tempo-example-backend`, and the stack passes the same value to `backend`.
- **Backend sessions:** `backend` keeps each session on its server with [`BackendSession`](../docs/guides/backend.md), so the browser holds only an opaque session ID in the `backend-sid` cookie. On Node, one instance for each app holds its sessions in memory, so a restart signs every user out of the app. On Cloudflare Workers, each app's session ID names a Durable Object, which holds the session in its storage. The sign-out revokes the refresh token at Tempo ID, and keeps Tempo ID's own session.
- **Tempo ID URL:** every playground reads `TEMPO_ID_URL` (`EXPO_PUBLIC_TEMPO_ID_URL` for `mobile`), which defaults to `http://localhost:5173`. `backend` also reads `TEMPO_ID_INTERNAL_URL`, where its server reaches Tempo ID, such as `http://id:5173` in the stack. `api` reads `TEMPO_ID_ISSUER`, the origin that tokens name, when it fetches keys from another URL.
- **Chain:** `web`, `third-party`, and `wagmi` sign in, fund, and send on Tempo mainnet, or on Tempo testnet when the **Network** toggle beside the title selects it. The toggle keeps its choice in `localStorage`, and `?chain=testnet` or `?chain=mainnet` sets it. With `TEMPO_RPC_URL`, they use the local chain, as the end-to-end suite runs, and show no toggle. `backend` and `cli` send on Tempo testnet, or on the local chain at `TEMPO_RPC_URL`. `mobile` reads `EXPO_PUBLIC_TEMPO_RPC_URL`, so it pays the stack's `api` on the same chain. In `pnpm dev`, the stack points `TEMPO_RPC_URL` at the [local chain](https://github.com/tempoxyz/id/blob/main/docs/development/local.md#local-chain). A `web` or `third-party` key on another chain sends and reads there through the playground Worker's `POST /rpc/<chainId>`, which forwards to that chain's `RPC_URLS` entry, else its public RPC URL, so no bundle holds a node's key. `vite dev` serves no `/rpc`, so only a build under `wrangler dev` or a deploy relays.
- **Client ID:** `web` and `wagmi` read `VITE_CLIENT_ID`, `backend` and `cli` read `CLIENT_ID`, and `mobile` reads `EXPO_PUBLIC_CLIENT_ID`. Each defaults to its seeded app. `CLIENT_ID=tempo-cli-cash` signs `cli` in to the Tempo Cash realm. `backend` reads a comma-separated list, whose first app is the default, and `/?client_id=` selects another for the browser session, as a preview's end-to-end suite does.
- **CLI:** run `cli` on the host with `pnpm --filter @tempoxyz/example-id-cli start <command>`: `login`, `whoami`, `fund`, `send <to> <amount>`, `pay [url]`, and `logout`. It stores its sign-in in `~/.config/tempo-id-playground/credentials.json`, or at `TEMPO_ID_CREDENTIALS`.
- **Permissions:** `web`, `wagmi`, `backend`, and `cli` read `PERMISSIONS`. Its value is JSON from ox's `Json.stringify` with any of `chainId`, `expiry`, `limits`, and `scopes`, such as `{"limits":[{"limit":"10000000#__bigint","token":"0x20c0000000000000000000006a37DA5C996874BE"}]}`. The web and wagmi playgrounds also have a form for them. Tempo ID fills what it leaves out with the [headless ceiling](https://github.com/tempoxyz/id/blob/main/docs/permissions.md#defaults). The playgrounds' own defaults add `open` and `topUp` on the channel reserve to the transfers, so the access key pays MPP sessions.
- **Permissions form:** the form of `web`, `wagmi`, and `third-party` adds token limits, each with an optional period, and scopes: `transfer`, `transferWithMemo`, which MPP charges call, and `approve` on a token, and `open` and `topUp` on the channel reserve, for MPP sessions. A custom call names any contract and function, which Tempo ID's approval page warns about. It lists the verified tokens of the selected chain from the Tempo API, at `https://api.tempo.xyz` for mainnet and testnet. `TEMPO_API_URLS` names the API of other chains as comma-separated `chainId=url` entries, such as `31318=https://api-t14-checkpoint.devnet.tempoxyz.dev`. The page's bundle holds these URLs, so the build refuses a URL with credentials, a path, or a query, and inlines only each origin. In `pnpm dev`, the stack reads them from `PLAYGROUND_TEMPO_API_URLS`, apart from Tempo ID's keyed `TEMPO_API_URLS`. A deploy reads each chain's first origin in the `TEMPO_API_URLS` secret, without its key, and leaves out an entry with a path or a query, so the page reads that chain from its default, if it has one.
- **MPP:** `api` serves MPP payments with mppx, in OUSD, to a payee of its own: `/mpp/charge` charges 0.01, `/mpp/proof` asks for a zero-amount proof, `/mpp/session` charges 0.01 for each request of a session, and `/mpp/stream` 0.005 for each streamed chunk. It pays on the local chain at `TEMPO_RPC_URL`, or on Tempo testnet. `MPP_PRIVATE_KEY` names the payee's key, and `MPP_SECRET_KEY` binds the challenges. On Node, each defaults to a key that the process generates. On Workers, the routes respond with 500 to every request until both are set, since a challenge from one isolate does not verify in another. The deploy derives both from the repository's `SECRET` and the deployment's suffix, so every isolate of a deployment holds the same values, and no one else holds them. On Workers, one Durable Object serves `/mpp/session` and `/mpp/stream`, and holds every channel in its storage, so a session outlives the isolate that opened it. Each process or object funds the payee from the chain's faucet before a session while the payee holds no OUSD, since the payee pays the fee of each session's close. The pages of `web`, `wagmi`, and `third-party` have an **MPP** section that pays each route with the access key: a charge in push or pull mode, a proof, requests and a stream of a session, and its close. On Tempo mainnet, which the routes do not serve, the section shows a notice and a **Switch to Testnet** button in place of the payments. `backend` pays a charge, and two requests of a session, from its server. `cli pay` pays a charge, or `--requests <n>` of a session, at `API_URL` or the URL it names. `mobile` pays a charge and the requests of a session. Each pays through the [`mpp` plugin](../docs/api/mpp.mpp.md), as the [MPP guide](../docs/guides/mpp.md) shows, so the access key signs each charge, voucher, and proof. `third-party` holds its sign-in itself, so it pays through an instance without a session, with `tempoId.mpp({ session })`. `cli pay` refuses a charge above `--max`, 0.1 by default. A proof succeeds only after the access key's first transaction, which registers it on chain.
- **Funding hint:** the redirect and dialog sign-ins of `web`, the redirect sign-in of `wagmi`, and every sign-in of `third-party` have a **Funding hint** form, and the signed-out page of `backend` has one too, which sends `/auth/start?funding_hint=…`. `cli login --funding 10` sends the hint with the device grant, with `--funding-currency` and `--funding-token`. Each sends `funding_hint`, `funding_currency`, and `funding_token`, as [Funding hints](https://github.com/tempoxyz/id/blob/main/docs/funding-hints.md) describes. An account that holds less than the amount opens Tempo ID's funding page after the approval. A dialog sign-in with a hint runs in a popup, since a frame cannot show the funding page. `web-cash` and `web-shared` reach the `tempo-cash` realm, so they receive no funding page.
- **Wagmi:** `wagmi` has the sign-ins, permissions form, funding hint, key, sections, transfers, API call, and wallet upgrade of `web`. Its instance holds the [`wagmi` plugin](../docs/api/wagmi.wagmi.md), whose config is the page's `WagmiProvider` config, with the instance as its one connector. Each sign-in through the instance connects wagmi, and **Sign out** disconnects wagmi, which signs out of Tempo ID. The page reads the connection and the balance through wagmi's hooks, sends with the access key through `Hooks.token.useTransferSync`, and signs through `useSignMessage` and `useSignTypedData`. A reload or a second tab reconnects from the saved session without a sign-in. wagmi sends only on the connection's chain, so a key on another chain reads there but sends nothing. The app is in the `default` realm, as `web` is, so the dialog and the page offer a passkey. The end-to-end suite registers it in `e2e-cash` too, which creates the key's account without the test Privy app.
- **Layout:** each page shares `web/style.css`: a centered column of sections, inline button rows, and folded details. The React playgrounds import it through `web/Layout.tsx`, and `backend` serves it at `/style.css`, which Wrangler imports as text. Signed out, a page names its sign-in methods. Each method's section folds its own **Permissions**, which that method's sign-ins read. The **Funding hint** offers the currencies and tokens of the chain in Viem's Tempo token list, and starts at USD with any USD token. Signed in, it shows these sections:

  | Section       | Contents                                                                                                        |
  | ------------- | --------------------------------------------------------------------------------------------------------------- |
  | Account       | The email, Tempo Account, and access key, **Call the API**, **Add passkey**, **Sign out**, and folded **Session details** |
  | Fund account  | The balance, and Tempo ID's deposit page in a popup or through a redirect, whose faucet funds a test chain's account |
  | Send payments | An OUSD transfer with the access key                                                                            |
  | Sign messages | A message and EIP-712 typed data, each verified on chain with `mode: 'allowAccessKey'`                           |
  | MPP           | A charge, and a session whose stream shows each paid word as it arrives                                          |

  `third-party` opens the deposit page only in a popup, since a redirect drops its sign-in. `backend` and `mobile` open it through a redirect, which returns to their registered redirect URI with `deposit_status`.
- **Mobile scheme:** `mobile` has no origin. The system browser returns to its `xyz.tempo.example.mobile:/callback` scheme, the redirect URI that the seed registers. Tempo ID serves no headless sign-in to a native app, so `mobile` signs in only through the system browser.
- **Mobile Metro config:** `metro.config.mts` is TypeScript, which Metro 0.84 loads with Node's type stripping.

## Deployments

`mobile` runs locally only. Each other playground but `cli` also runs on Cloudflare Workers through its `wrangler.jsonc`, and `api` and `backend` through their `worker.ts`. The deploy workflow deploys them beside production at `https://id-playground-<name>.tempo.xyz`, and beside each pull request's preview at `https://id-playground-<name>-pr-<n>.<subdomain>.workers.dev`, as the [development docs](https://github.com/tempoxyz/id/blob/main/docs/development/deploys.md) describe.

Each pull request also publishes `cli` as the public npm prerelease `@tempoxyz/example-id-cli@0.0.0-pr-<n>.sha-<commit>`, beside the same prerelease of `accounts`, under the dist-tag `pr-<n>`. The preview comment names the `npx` commands that run `cli` and `tempo-id login` against the preview. The workflow publishes through npm trusted publishing. Until the `NPM_TRUSTED_PUBLISHING` repository variable is `true`, it publishes nothing, and the comment names no prerelease.

## Limitations

- On Node, `api` holds each MPP session's channel in memory, so a restart loses every open channel. A page's session manager also holds its channel in memory. The page closes an open channel at a sign-out or a new access key, but a reload leaves the channel and its deposit open.
- Tempo ID fetches the `third-party` document from its public URL. In `pnpm dev`, that is `https://playground-third-party--<hash>.tempo.local`, which Tempo ID's container reaches only when it trusts OrbStack's certificate authority. No end-to-end spec drives `third-party` yet.
- `web`, `backend`, and `mobile` request a key at their redirect sign-in, and the approval of the key creates a new user's first Tempo Account. This needs a Privy app or secp256k1 owners in the app's first realm. Without either, the approval page offers only **Deny**. `VITE_KEY=false` for `web` and `wagmi`, and `KEY=false` for `backend` sign in without a key. A signed-in user without a key then selects **Authorize an access key**. In `web` and `wagmi`, the dialog shows the key on the approval page on the playground's own page. `backend` shows it after a second redirect.
- The approval page signs no key for an account that a passkey owns, and offers only **Deny**. When Tempo ID refuses a key, each playground signs in again without one: `web` headlessly, and `backend` and `mobile` through a second redirect, which on iOS asks the user to sign in again. When a headless key needs the passkey, `web` and `wagmi` sign in headlessly without a key and offer **Authorize an access key**. `web` and `wagmi` open Tempo ID's pages only from **Sign in via redirect**.
- `mobile` opens the deposit page in the system browser. On iOS, the sign-in's browser session is ephemeral, so the deposit page signs the user in again and then opens the account page, which never returns to the app. On a test chain, **Faucet** funds the account in the app instead.
- On Android, the sign-out of `mobile` leaves Tempo ID's session in the browser, so the next sign-in continues as the same user. iOS uses an ephemeral browser session, which keeps none.
- The end-to-end suite runs no Tempo node yet, so no test funds or sends.
- A headless key needs a Privy-owned account, so `web` signs keys headlessly only in a realm with a Privy app, such as `default` with the test Privy app from `pnpm env:pull`. The emailed-code and passkey sign-ins create a new user's account first.
